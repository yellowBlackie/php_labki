# Практична робота №7

## Варіант 4 — Фітнес-трекер

Мета роботи — дослідити продуктивність PHP API під навантаженням, знайти проблему N+1 та виконати оптимізацію SQL-запитів.

## Структура роботи

```text
lab7/
├── api.php
├── before_nplus1.php
├── benchmark_cleanup.sql
├── benchmark_seed.sql
├── create_index.sql
├── csrf.php
├── db.php
└── README.md
```

Файл `before_nplus1.php` містить реальну версію коду до оптимізації з N+1.

Файл `create_index.sql` містить реальні `EXPLAIN` та `CREATE INDEX`.

Файл `benchmark_seed.sql` додає 300 тестових записів для повторного навантажувального тесту.

---

## 1. Варіант до оптимізації

Endpoint:

```text
before_nplus1.php
```

Спочатку виконується один SQL-запит для отримання списку тренувань, а потім для кожного тренування виконується ще один запит:

```sql
SELECT COALESCE(SUM(calories_burned), 0)
FROM workouts
WHERE type = :type;
```

Тому при `N` записах виконується:

```text
1 + N SQL-запитів
```

Наприклад, для 8 тренувань це було 9 SQL-запитів.

---

## 2. Оптимізація N+1

В оптимізованому `api.php` окремі запити в циклі замінені одним агрегатним запитом:

```sql
SELECT type, SUM(calories_burned) AS total_calories
FROM workouts
GROUP BY type;
```

Після цього дані зіставляються з тренуваннями вже в PHP.

Без кешу виконується:

```text
2 SQL-запити
```

З актуальним кешем:

```text
1 SQL-запит
```

---

## 3. Індекс для поля type

До створення індексу виконується:

```sql
EXPLAIN
SELECT *
FROM workouts
WHERE type = 'Біг';
```

Потім:

```sql
CREATE INDEX idx_workouts_type
ON workouts (type);
```

І після цього `EXPLAIN` виконується повторно.

Увесь SQL збережено окремо у файлі:

```text
create_index.sql
```

---

## 4. Кешування

Для сумарних калорій за типами реалізований файловий кеш з TTL 60 секунд.

У профілюванні відповідь містить:

```text
totals_from_cache: false
```

коли виконується `GROUP BY`, та:

```text
totals_from_cache: true
```

коли агреговані дані отримані з кешу.

Після додавання тренування кеш очищається.

## 5. Тестові дані для benchmark

Щоб не робити замір лише на кількох записах, використовується файл:

```text
benchmark_seed.sql
```

Після завершення тестів їх можна видалити:

```text
benchmark_cleanup.sql
```

## 6. Apache Bench

Для чесного порівняння обидва тести потрібно виконувати на одній і тій самій базі даних після додавання 300 тестових записів.

### До оптимізації

```powershell
& "D:\papka1\apache\bin\ab.exe" -l -n 200 -c 20 "http://localhost/labki_php/lab7/before_nplus1.php"
```

### Після оптимізації

Спочатку один раз відкрийте оптимізований endpoint, щоб прогріти кеш:

```text
http://localhost/labki_php/lab7/api.php?resource=workouts
```

Потім:

```powershell
& "D:\papka1\apache\bin\ab.exe" -l -n 200 -c 20 "http://localhost/labki_php/lab7/api.php?resource=workouts"
```

## 7. CSRF та валідація

POST-запити створення тренування і `action=stats` захищені CSRF-токеном.

Отримати токен:

```powershell
curl.exe -s -c lab7_cookie.txt "http://localhost/labki_php/lab7/api.php?resource=workouts&action=csrf"
```

POST без токена повертає:

```text
403 Forbidden
```

Також на сервері перевіряються обов'язкові поля, додатна тривалість, невід'ємні калорії та формат дати.

---

## Висновок

У роботі збережено обидві версії реалізації: до оптимізації з N+1 та після оптимізації.

Проблему N+1 усунуто за допомогою одного агрегатного `GROUP BY`, для `type` додано індекс, а агреговані результати кешуються на 60 секунд.

Для повторного benchmark використовується значно більший набір тестових даних, щоб різниця між двома реалізаціями була помітною.
