# Практична робота №7

## Варіант 4 — Фітнес-трекер

### Мета роботи

Дослідити продуктивність PHP API під навантаженням, виміряти час виконання та використання пам'яті, знайти проблему N+1, додати індекс у базу даних, оптимізувати кількість SQL-запитів і реалізувати кешування.

Для роботи використовується endpoint:

```text
http://localhost/labki_php/lab7/api.php?resource=workouts
```

---

## 1. Початковий варіант

У початковій версії була спеціально реалізована проблема N+1.

Спочатку виконувався один SQL-запит для отримання всіх тренувань:

```sql
SELECT id, type, duration_min, calories_burned, workout_date
FROM workouts
ORDER BY workout_date DESC, id DESC;
```

Після цього для кожного тренування окремо виконувався запит для підрахунку сумарних калорій тренувань такого самого типу:

```sql
SELECT COALESCE(SUM(calories_burned), 0)
FROM workouts
WHERE type = :type;
```

У таблиці було 8 тренувань.

Тому кількість SQL-запитів становила:

```text
1 + 8 = 9 SQL-запитів
```

Результат профілювання:

```text
execution_time_ms: приблизно 4–6 ms
peak_memory_mb: 2
sql_queries: 9
```

Перший запуск був повільнішим і становив приблизно:

```text
34.409 ms
```

При повторних запусках час був:

```text
6.025 ms
4.012 ms
```

## 2. Apache Bench до оптимізації

Для навантажувального тестування використовувався Apache Bench.

Команда:

```bash
"D:\papka1\apache\bin\ab.exe" -l -n 200 -c 20 "http://localhost/labki_php/lab7/api.php?resource=workouts"
```

Параметри:

```text
-n 200 — загальна кількість запитів
-c 20  — кількість одночасних запитів
-l     — дозволяє змінну довжину відповіді
```

Результат тестування:

```text
Complete requests:      200
Failed requests:        0
Requests per second:    684.29 [#/sec]
Time per request:       29.227 [ms]
Concurrency Level:      20
```

## 3. Перевірка індексу

Для варіанта 4 індекс потрібно було створити для поля:

```text
type
```

Спочатку було виконано:

```sql
EXPLAIN
SELECT *
FROM workouts
WHERE type = 'Біг';
```

Результат до створення індексу:

```text
type: ALL
possible_keys: NULL
key: NULL
rows: 6
```

Це означає, що MySQL виконував повне сканування таблиці.

Після цього було створено індекс:

```sql
CREATE INDEX idx_workouts_type
ON workouts (type);
```

Потім знову було виконано:

```sql
EXPLAIN
SELECT *
FROM workouts
WHERE type = 'Біг';
```

Результат після створення індексу:

```text
type: ref
possible_keys: idx_workouts_type
key: idx_workouts_type
rows: 2
Extra: Using index condition
```

Після створення індексу MySQL почав використовувати `idx_workouts_type`, а кількість рядків для перевірки зменшилась.

---

## 4. Усунення проблеми N+1

Замість виконання окремого SQL-запиту для кожного тренування був використаний один агрегатний запит:

```sql
SELECT type, SUM(calories_burned) AS total_calories
FROM workouts
GROUP BY type;
```

Після цього отримані значення додаються до тренувань вже на стороні PHP без додаткових SQL-запитів.

У результаті кількість запитів змінилась:

```text
До оптимізації: 9 SQL-запитів
Після GROUP BY: 2 SQL-запити
```

Один запит отримує список тренувань, другий — сумарні калорії для кожного типу.

---

## 5. Кешування

Для агрегованого результату було реалізовано файловий кеш.

Час життя кешу:

```text
60 секунд
```

При першому запиті, коли кеш ще не створений або вже застарів:

```text
sql_queries: 2
totals_from_cache: false
```

При повторному запиті:

```text
sql_queries: 1
totals_from_cache: true
```

У цьому випадку агреговані значення беруться з кешу, тому додатковий SQL-запит з `GROUP BY` не виконується.

Після додавання нового тренування кеш очищається, щоб не використовувати застарілі дані.


```text

```

Time per request зменшився:

```text

```

## Висновок

У ході роботи було проведено профілювання PHP API та навантажувальне тестування за допомогою Apache Bench.

Було знайдено проблему N+1, через яку для 8 тренувань виконувалось 9 SQL-запитів.

Для оптимізації було створено індекс для поля `type`, замінено окремі SQL-запити одним агрегатним запитом з `GROUP BY` та реалізовано файловий кеш з TTL 60 секунд.

Після оптимізації кількість SQL-запитів при використанні кешу зменшилась з 9 до 1. Також збільшилась кількість запитів, які сервер може обробити за секунду, а середній час одного запиту зменшився.

Отже, використання індексу, агрегатних запитів і кешування дозволило зменшити навантаження на базу даних та покращити продуктивність API.
